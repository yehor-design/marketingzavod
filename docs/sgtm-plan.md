# Server-side GTM: план і порівняння хостингу

Відкладена навчальна задача. Серверний контейнер коштує грошей щомісяця, тому рішення про старт за Єгором. Цей документ закриває лише перший крок: порівняння і рекомендацію.

## Навіщо

Серверний контейнер приймає події на власному піддомені (`sgtm.heywowboy.com`) і вже звідти розсилає їх у GA4, Google Ads і Meta. Що це дає: cookies ставить сервер, тому вони живуть довше в Safari; менше втрат через блокувальники; ключі та логіка не в браузері.

Що вже є без нього: Meta Conversions API працює з route handler Next.js, PostHog іде через власний домен `/ingest`. Тобто головну користь серверного трекінгу для Meta сайт уже має.

## Рекомендація

Для навчального стенда: **Stape, план Free**, з переходом на Pro, якщо запитів стане більше 10 тис. на місяць. Сайт із трафіком до кількох тисяч візитів на місяць вкладається у Free, якщо через сервер іде лише GA4 і конверсії. Cloud Run виправданий, коли є вимога тримати все у власному хмарному акаунті.

Якщо реклама не запускається найближчими місяцями, серверний контейнер варто відкласти: він не дасть користі без трафіку.

## Що буде після рішення (ще не зроблено)

1. DNS: запис для `sgtm.heywowboy.com`. Для Stape це CNAME на адресу, яку він видасть. Для Cloud Run це запис, який покаже мапінг домену.
2. GA4: у Google tag додати `server_container_url = https://sgtm.heywowboy.com`. У серверному контейнері налаштувати клієнт GA4 і теги GA4, Google Ads, Meta CAPI.
3. Meta: перенести Conversions API з route handler у серверний контейнер або лишити обидва за перемикачем у змінній середовища. Подвійного надсилання бути не може.
4. Перевірити передавання згоди (`gcs`, `gcd`) у серверний контейнер і дедуплікацію.
5. Порівняти кількість подій за тиждень до і після.

Ці кроки потребують акаунта хостингу, серверного контейнера GTM і DNS-запису. Їх робить Єгор, після чого задачу можна продовжити.
